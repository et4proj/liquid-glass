# npm 包名方案分析

## 先回答第一个问题：`@et4proj/liquid-glass/core` 不能作为独立包发布

npm 的 scoped 包名规则只支持**一级 scope**：`@scope/package-name`，包名中不允许出现第二个 `/`。`@et4proj/liquid-glass/core` 不是合法包名，无法发布。

但注意：这个**导入路径形状**是可以通过“单包 + `exports` 子路径”实现的——即只发布一个包 `@et4proj/liquid-glass`，在它的 `package.json` 里声明 `"./core": "./dist/core.js"` 等子路径，用户就能写 `import ... from '@et4proj/liquid-glass/core'`。这是 Vue（`vue/compiler-sfc`）、Babel（`@babel/core` 是独立包但都是一级）之外少数场景用的模式。它是**一个包**，不是多个包。

## 三个候选方案对比

|                | A. 二级 scope<br>`@et4proj-liquid-glass/core`                                                                                | B. 单 scope + 前缀<br>`@et4proj/liquid-glass-core`                    | C. 单包 + exports 子路径<br>`@et4proj/liquid-glass` 的 `./core`                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 合法性         | 合法，但 `@et4proj-liquid-glass` 是一个**独立 scope**，npm 公开发布需要在 npmjs.com 上拥有名为 `et4proj-liquid-glass` 的组织 | 合法，直接用你现有的 `@et4proj`                                       | 合法                                                                                        |
| 组织管理       | 为每个项目新建 org，权限、成员、发布 token 分裂；org 数量随项目膨胀                                                          | 全部包归在一个组织下，npm 组织页可集中展示                            | 同 B                                                                                        |
| 生态惯例       | 无先例                                                                                                                       | 主流做法：`@vueuse/core`、`@tanstack/react-query`、`@reduxjs/toolkit` | 仅适合“单包产品”（如 `vue`）；不适合多包架构                                                |
| 按需安装       | 可以                                                                                                                         | 可以                                                                  | **不行**——装一个包全量带上所有适配包                                                        |
| 适配包独立演进 | 可以                                                                                                                         | 可以                                                                  | **不行**——adapter 要按组件库 `versionRange` 独立发版（文档 §7.2），单包会被核心版本节奏绑死 |
| 重后端按需拆包 | 可以                                                                                                                         | 可以                                                                  | **不行**——unplugin、cli、webgl 后端依赖全耦合                                               |

**结论：选 B，果断排除 A 和 C。**

排除 A 的核心理由：你已经有 `@et4proj` 这个组织，`@et4proj-liquid-glass` 意味着再注册一个组织——scope 在 npm 上与组织名绑定，这会让你的包永久分散在两个“组织”下，管理成本翻倍且无任何收益。连字符伪造的“层级”只是视觉安慰，npm 并没有真正的层级语义。

排除 C 作为主方案的理由：你的架构文档 §3.3 明确是多包路线（适配包独立演进、构建插件独立依赖、重后端按需拆包），单包模式与这三点直接冲突。

## 推荐命名方案

| 目录（`packages/`） | 包名                                 | 说明                                                                                                                       |
| ------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `core/`             | `@et4proj/liquid-glass-core`         | M0 主力：契约类型 + token + resolve                                                                                        |
| —（预留）           | `@et4proj/liquid-glass`              | **预留为聚合主包**，M1 做 core+web 的统一入口，Web 用户装一个包即可（类似 `@tanstack/react-query` 聚合 query-core 的模式） |
| `web/`              | `@et4proj/liquid-glass-web`          | Web 探针 + css/svg/webgl 后端                                                                                              |
| `vue/`              | `@et4proj/liquid-glass-vue`          | v-glass / useGlass / `<Glass>`                                                                                             |
| `react/`            | `@et4proj/liquid-glass-react`        |                                                                                                                            |
| `adapter-vant/`     | `@et4proj/liquid-glass-adapter-vant` | 后续按库追加                                                                                                               |
| `unplugin/`         | `@et4proj/unplugin-liquid-glass`     | 包名主体保留 `unplugin-` 前缀，可被 unplugin 生态索引识别（`@vitejs/plugin-vue` 同款惯例）                                 |
| `cli/`              | `@et4proj/liquid-glass-cli`          | `bin` 名用 `liquid-glass`（bin 名全局唯一，若被占则退 `lglass`）                                                           |
| `mp/`、`bridge/`    | `@et4proj/liquid-glass-mp` 等        | M3/M4 再建                                                                                                                 |

两个设计要点：

1. **目录用短名，包名带前缀**：`packages/core` 而不是 `packages/liquid-glass-core`，import 路径和目录引用都干净（`workspace:*` 协议按包名引用，不受目录名影响）。
2. **`@et4proj/liquid-glass` 这个名字先占住不发**：M0 只发 `-core`。等 M1 有了 web 后端再发布聚合包，避免“主包先发成 core、以后拆分破坏已发布 API”的坑。

这样你既保住了 `@et4proj/liquid-glass` 作为主包名的心智，又完全符合 npm 规则和多包架构需求。

消费者（css/svg/webgl 后端、增强件）←──GlassTokens（通道化输出）

- **未知字段自动透传插值**：风格包可先行加数据，消费者后落地（M2 WebGL 的色差参数现在就能进 ios27 包）。

好问题——先澄清一个关键点：**CSS 变量从来不是 token 的“形态”，它只是 CSS 后端的一种投影（transport）**。当前体系里 token 的权威形态本来就是 TS/JS 对象（`resolve` 输出的 `MaterialTokens`），`tokensToCssVars` 只是把 JS 对象翻译给 DOM 渲染路径消费。所以不存在“换成 JSON/JS”的问题，真正的问题是**每一层该用什么形态**。

## 三层形态分析

```
定义层   风格包 StylePack ──── TS/JS 模块（v2 提案，可独立发布）
              │ registerStyle
运行时层 GlassTokens ──────── JS 对象（唯一权威，平台无关 ← 硬约束 #2）
              │ 各后端自行投影
投影层   ┌─ CSS 后端 → CSS 自定义属性（--glass-*）
        ├─ SVG 后端 → CSS 变量 + filter scale 参数
        ├─ WebGL（M2）→ shader uniforms（每帧 uniform2f）
        ├─ 小程序（M3）→ 直接消费 JS 对象（CSS 变量在小程序支持残缺）
        └─ Native bridge（M4）→ JSON 序列化过桥
```

各格式的定位与边界：

| 形态           | 定位                    | 赢在哪里                                                                                                                                              | 输在哪里                                                                 |
| -------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **JS/TS 对象** | 运行时权威 + 风格包源码 | 类型安全；可表达函数（v2 的自定义 `interpolate` 只有 JS 能写）；tree-shakable；可派生计算                                                             | 不能直接跨语言/跨进程                                                    |
| **JSON**       | 交换格式                | 配置文件（unplugin/CLI 的 `liquid-glass.config.json`）；**风格远程下发**（iOS 28 参数热更新，不用发版）；M4 bridge 协议                               | 要 parse、无类型、**表达不了函数**                                       |
| **CSS 变量**   | DOM 渲染投影            | 运行时可变（updateConfig 写变量即时生效，零规则重算）；参与级联（用户可在容器级覆盖 `--glass-blur`）；per-element 隔离，多表面不同参数共存；绘制零 JS | 字符串类型（数值须格式化）；只能扁平标量（通道对象须拍平）；小程序不可用 |
| **静态 CSS**   | 编译期投影              | unplugin L0 产物，零运行时 JS                                                                                                                         | 不能动态（能力降级、强度切换都失效），只适合最终形态固定的场景           |
| **uniforms**   | WebGL 投影              | 每帧一次 uniform 更新驱动整套光学参数                                                                                                                 | 仅 GPU 路径                                                              |

## 结论

1. **不换**。JS 对象继续做唯一权威运行时形态（core 平台无关约束天然要求如此）；CSS 变量保持为 CSS 后端的投影，不越界。
2. **JSON 作为交换格式显式纳入 v2**：风格包数据必须保持 **JSON-safe**（纯数据），`interpolate` 函数是唯一非序列化的可选增强——这样同一份 ios27 风格既能以 JS 包发布，也能序列化后远程下发（对齐 iOS 27 官方“滑杆参数系统级可调”的思路，为未来的远程风格配置留路）。
3. 通道对象进 CSS 语境时按 `--glass-<channel>-<field>` 拍平（如 `--glass-refraction-strength`），仅后端需要的字段才投影，不全量倾倒。
